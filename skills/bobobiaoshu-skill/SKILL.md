# 小波标书助手V9.0

投标技术标文档自动生成工具。三级解析 → 深度分析 → 评分映射 → 必含标题检测 → Token/时间估算 → 基于模板生成 → 去 AI 痕迹 → 输出 Word。

---

## 执行流程（标准）

```
⓪ 首次使用检查（config_manager.py check）→ 无 config.json 时执行首次配置引导 → 后续自动加载
① 接收招标文件 + 用户提供 Word 模板（若 config.json 已配置 template_path，自动使用）
② 必须询问用户：目标总页数是多少页？是否需要在正文中添加表格、图表等内容（会增加 token 消耗）？
③ 三级解析招标文件（parse_bid_files.py v4.0，自动降级策略，输出 Markdown 表格 + 项目信息 + 元数据）
④ 招标文件深度分析（bid_analysis.py）→ 生成10节分析报告（项目信息/时间节点/采购需求/评分标准/商务条款/投标重点/技术难点/风险提示/特别条款/竞争态势）
⑤ 评分点自动映射（eval_mapping.py report）→ 解析评分标准、自动映射到章节、生成覆盖检查报告 + 字数分配表
⑥ 【★必做】必含标题检测（eval_required_headings.py report）→ 扫描「包括但不限于」「至少包含」等模式，提取枚举项作为强制 H2 标题，检查大纲覆盖
⑦ 提取模板格式参数（template_extractor.py）
⑧ 【加速】搜索片段库匹配通用章节 → 相关性预筛（relevance_check.py，弃用低分片段）→ 预填充大纲
⑨ 生成4级标题详细大纲 → 必须包含步骤⑥检测到的所有必含 H2 标题 → Token/时间估算（estimate_tokens.py）与大纲一并展示 → **必须等待用户确认后才能继续**（对照评分点映射表+必含标题检查报告逐条确认全覆盖，用户明确回复"通过"后方可进入步骤⑩）
⑩ 审核通过后并发编写各章节（已有片段的：load → adapt check → relevance check → 改写；无片段的从零编写）。若步骤②用户选择添加表格图表，编写时在各章节适当位置插入表格和图表描述
⑪ 章节字数检查（check_chapter_words.py，必须执行）
⑫ 去 AI 痕迹（必须执行，参见 references/de-ai-rules.md + humanizer-zh.md，使用上下文感知替换策略）
⑬ 内容相关性检查（必须执行）
⑭ 片段残留检查（snippet_adapt.py check，必须执行）— 检查改写后的内容是否残留原项目字眼
⑮ 汇总整合（merge_chapters.py）→ 基于模板转换 Word（convert_to_word.py --template，自动注入标题编号 numPr）
⑯ 文档质量全检查（doc_quality_check.py + 必含标题验证，必须执行）
⑰ 【保存】抽取通用片段存入 memory（snippet_manager.py save，路径从 config.json 读取）
⑱ 任务完成通知用户
```

## 首次使用配置（Step 0）

首次在本机使用本技能时，必须先完成首次配置。配置保存在 skill 目录下 `config.json`，后续使用自动加载。

### 配置检查

每次开始标书任务前，先执行配置检查：

```bash
python scripts/config_manager.py check
```

- 输出 `CONFIG_EXISTS`：加载配置，跳到步骤①正常流程
- 输出 `CONFIG_NOT_FOUND`：执行首次配置引导

### 首次配置引导

检测到 `CONFIG_NOT_FOUND` 时，向用户依次收集以下信息：

| 序号 | 配置项 | 说明 | 示例 |
|------|--------|------|------|
| 1 | memory 名称 | 用于创建片段库和术语库的存储目录名称 | `2026招投标` |
| 2 | 标书模板路径 | Word 模板 .docx 文件路径，后续生成标书时自动使用 | `C:/Users/xxx/Desktop/模板.docx` |
| 3 | 历史标书路径 | 存放历史标书的目录（可选），用于自动分析提取片段和术语 | `C:/Users/xxx/Desktop/历史标书` |
| 4 | 默认输出目录 | 标书终稿默认保存路径 | `C:/Users/xxx/Desktop/2026招投标/输出` |
| 5 | 行业类型 | 影响片段库分类和术语库种子内容 | 电信/IT/建筑/交通/金融/其他 |

收集完成后执行初始化：

```bash
python scripts/config_manager.py init \
  --memory-name "2026招投标" \
  --template "C:/Users/xxx/Desktop/模板.docx" \
  --output "C:/Users/xxx/Desktop/2026招投标/输出" \
  --industry telecom \
  --history "C:/Users/xxx/Desktop/历史标书"
```

初始化时会自动：
- 创建 `{桌面}/{memory名称}/memory/` 目录结构（snippets/、vocabulary/、outlines/、projects/）
- 根据行业类型创建默认片段分类目录
- 生成行业术语种子文件（vocabulary/术语表.md）
- 创建输出目录
- 保存 config.json

### 历史标书自动分析

若用户提供了历史标书路径，初始化完成后询问用户：**是否立即分析历史标书以构建片段库和术语库？**

```bash
python scripts/snippet_manager.py save <解析结果.md> --category 风险评估

# 4. 从文档中提取行业术语，追加到术语表
# （agent 手动提取关键术语，追加到 memory/vocabulary/术语表.md）
```

### 必等项：大纲人工确认

**生成技术部分大纲后，必须暂停并等待用户确认。** 不可跳过，不可自动继续。

确认流程：
1. 展示大纲 + 评分点映射表给用户
2. 展示必含标题检查报告（eval_required_headings.py 输出），标明缺失项
3. 展示 Token/时间估算报告（estimate_tokens.py 输出），让用户预知 token 用量和编写耗时
4. 请用户逐条核对评分点是否全部覆盖、必含标题是否全部包含
5. 用户明确回复"通过"/"确认"/"可以"后，方可进入章节编写
6. 用户要求修改时，调整大纲后重新提交确认

### ★ 必含标题检测（包括但不限于）

**招标文件中出现「包括但不限于」「至少包含」「应包括」等措辞时，其后枚举的每一项都必须作为对应章节的 H2 标题出现。** 这是评分的硬性要求，缺失会导致评分项不覆盖。

常见模式：
- `工作进度及控制方案包括但不限于：满足程度、进度安排、实施人员安排`
- `培训内容应包括但不限于以下方面：1.技术原理 2.性能 3.操作使用方法...`
- `驻点人员管理应包括：企业管理制度、现场人员管理措施、安全管理措施、应急预案`

检测脚本自动完成扫描和检查：

```bash
# 一键扫描+检查（推荐）
python scripts/eval_required_headings.py report <招标文件解析结果.md> --outline <大纲.md> --output <输出目录>

# 仅扫描招标文件
python scripts/eval_required_headings.py scan <招标文件解析结果.md> --output required_headings.json

# 仅检查大纲覆盖
python scripts/eval_required_headings.py check required_headings.json --outline <大纲.md>
```

**执行规则：**
1. 步骤⑥生成大纲前，先运行 `eval_required_headings.py scan` 扫描招标文件
2. 生成大纲时，将检测到的必含项作为 H2 标题写入对应章节
3. 步骤⑨展示大纲时，附上必含标题检查报告
4. 步骤⑯生成 Word 后，再次运行 `check` 验证最终文档覆盖

### Token/时间估算

大纲生成时一并展示 Token 消耗和编写时间预测，帮助用户决策：

```bash
python scripts/estimate_tokens.py estimate <大纲.md> --pages <目标页数> --eval <eval_criteria.json> [--with-tables] [--output <估算报告.md>]
```

估算模型：
- 每页约 780 中文字符
- 输入 token：每章约 6000（招标文件上下文+大纲指令+片段）
- 输出 token：字数 × 1.3（添加表格图表时 × 1.5）
- 去 AI 痕迹 token：字数 × 0.3
- 编写速度：约 600 字/分钟，4 章并发
- `--with-tables`：输出 token 系数 1.3→1.5，输入 token +5%，模拟表格图表内容的额外 token 开销

字数计算公式：`目标字数 = 评分分值 × (总页数 ÷ 总分) × 780`
合格范围：`目标 × 0.75 ~ 1.25`

| 分值 | 目标字数(400页基准) | 合格范围 |
|------|-------------------|---------|
| 5分  | 20,000字 | 15,000~25,000字 |
| 4分  | 16,000字 | 12,000~20,000字 |
| 3分  | 12,000字 | 9,000~15,000字 |

不达标 → 打回对应章节重写 → 达标后继续

> eval_mapping.py report 会自动生成字数分配表，无需手动计算。

## 招标文件解析（三级降级策略）

### 解析优先级

| 级别 | 方法 | 适用场景 | 特点 |
|------|------|----------|------|
| 第一级 | 本地解析 (pdfplumber/python-docx/openpyxl) | 文本型 PDF、Word、Excel | 快速、离线 |
| 第二级 | MarkItDown (微软开源) | 复杂格式、PPT、HTML、结构保留 | 格式覆盖广、结构好 |
| 第三级 | 星辰 OCR API (xc-doc-parser) | 扫描版 PDF、图片 | 高精度 OCR、处理扫描件 |

### 降级逻辑

```
本地解析 → 成功？→ 使用结果
         → 失败/不足50字？→ MarkItDown
                           → 成功？→ 使用结果
                           → 失败？→ 星辰 OCR
                                     → 成功？→ 使用结果
                                     → 失败？→ 报错，提示手动处理
```

### v4.0 新增功能

| 功能 | 说明 |
|------|------|
| Markdown 表格输出 | 表格不再以 `[表格]` 前缀输出，改为标准 Markdown 管道表格格式（`| col1 | col2 |`），修复 eval_mapping.py 兼容性 |
| PDF 表格提取 | 使用 pdfplumber `extract_tables()` 提取 PDF 表格数据并输出为 Markdown 表格 |
| 项目信息提取 | 自动提取项目名称、招标编号、招标人、预算金额、投标截止时间等关键信息 |
| 文档元数据 | 输出页数、字符数、表格数、标题数等结构化元数据 |
| 章节树重建 | 基于标题层级重建文档目录结构 |

### 使用命令

```bash
# 自动选择最佳解析方式（推荐）
python scripts/parse_bid_files.py <文件路径>

# 指定输出目录
python scripts/parse_bid_files.py <文件路径> --output <输出目录>

# 限制解析级别（1=仅本地, 2=+MarkItDown, 3=+星辰OCR）
python scripts/parse_bid_files.py <文件路径> --level 3
```

解析结果输出 `.md` 文件，同时生成 `{basename}_项目信息.json` 文件（含项目名称、编号、招标人等结构化信息）。

### 支持格式

| 格式 | 本地解析 | MarkItDown | 星辰 OCR |
|------|:-------:|:---------:|:-------:|
| .txt | ✅ | - | - |
| .docx | ✅ | ✅ | - |
| .pdf (文本型) | ✅ | ✅ | ✅ |
| .pdf (扫描版) | ❌ | ❌ | ✅ |
| .xlsx/.xls | ✅ | ✅ | - |
| .pptx | ❌ | ✅ | - |
| .jpg/.png/.bmp/.webp | ❌ | ✅(OCR) | ✅ |
| .html | ❌ | ✅ | - |

### 星辰 OCR 依赖

扫描版 PDF 和图片解析需要 xc-doc-parser 技能。脚本自动查找以下路径：
- `skills/xc-doc-parser/scripts/document_parser.py`
- 环境变量 `TELEAGENT_CONFIG_DIR` 下的 skills 目录

文件限制：10MB 以内。超出需先拆分。

## 招标文件深度分析（bid_analysis.py）

在解析招标文件后、编写标书前，生成 10 节结构化分析报告，为后续编写提供决策支持。

### 与 eval_mapping.py 的区别

| 维度 | bid_analysis.py | eval_mapping.py |
|------|----------------|----------------|
| 定位 | 招标文件全局分析 | 评分点→章节映射 |
| 时机 | 编写前（决策支持） | 编写中（覆盖检查） |
| 输出 | 10 节分析报告 | 评分点映射表 + 覆盖检查报告 + 字数分配表 |
| 关注点 | 风险/重点/竞争态势 | 评分点覆盖完整性 |

### 使用命令

```bash
# 基本用法（从解析结果生成分析报告）
python scripts/bid_analysis.py <解析结果.md> --output <输出目录>

# 传入项目信息 JSON（更准确）
python scripts/bid_analysis.py <解析结果.md> --info <项目信息.json> --output <输出目录>
```

### 报告内容（10 节）

| 章节 | 内容 |
|------|------|
| 1. 基本信息摘要 | 项目名称、编号、招标人、预算、服务期（表格） |
| 2. 时间节点梳理 | 投标截止、开标时间、服务期等（表格） |
| 3. 采购需求与技术规格 | 按章节提取的技术要求（列表） |
| 4. 评分标准深度解析 | 评分项、分值、占比（表格） |
| 5. 商务条款与投标要求 | 资格审查、保证金等（检查清单） |
| 6. 投标重点分析 | 按分值排序 Top 5 评分项 |
| 7. 技术难点分析 | 针对评分项给出编写建议 |
| 8. 潜在风险提示 | 无效投标/废标/围标串标等风险（红黄绿三级） |
| 9. 需特别关注的条款 | ★标记条款、强制要求 |
| 10. 综合竞争态势分析 | 分类评分占比 + 竞争建议 |

## 评分点自动映射（eval_mapping.py）

解析招标文件中的评分标准，自动映射到技术标章节大纲，生成覆盖检查报告和字数分配表。

### 工作流程

```
招标文件解析结果.md → eval_mapping.py parse → eval_criteria.json
                                        ↓
                   大纲.md → eval_mapping.py map → 评分点映射表.md
                                        ↓
                              eval_mapping.py check → 覆盖检查报告
```

### 使用命令

```bash
# 一步到位：解析 + 映射 + 覆盖检查（推荐）
python scripts/eval_mapping.py report <招标文件解析结果.md> --outline <大纲.md> --output <输出目录>

# 分步执行
# 1. 解析评分标准
python scripts/eval_mapping.py parse <招标文件解析结果.md> --output eval_criteria.json

# 2. 映射评分点到章节
python scripts/eval_mapping.py map eval_criteria.json --outline <大纲.md> --output 评分点映射表.md

# 3. 覆盖检查
python scripts/eval_mapping.py check eval_criteria.json --outline <大纲.md>
```

### 外部评分文件（--scoring）

PDF 招标文件中的评分表格可能无法被 pdfplumber 正确解析。此时可手动整理评分标准为 Markdown 表格，通过 `--scoring` 参数传入：

```bash
python scripts/eval_mapping.py report <招标文件.md> --scoring <评分标准.md> --outline <大纲.md> --output <输出目录>
```

评分标准文件格式（管道表格）：

```markdown
| 序号 | 评分因素 | 分值 | 评分标准说明 |
|------|---------|------|------------|
| 1 | 项目理解 | 5 | 对项目背景的理解程度... |
| 2 | 技术方案 | 20 | 方案的完整性、可行性... |
```

### 输出内容

| 输出文件 | 内容 |
|---------|------|
| `eval_criteria.json` | 结构化评分数据（总分、分类、评分项列表、项目信息） |
| `评分点映射表.md` | 评分点-章节对照表 + 覆盖状态 + 字数分配表 |
| `eval_mapping_result.json` | 完整映射结果（JSON 格式，含匹配分数） |

### 覆盖状态说明

| 状态 | 匹配分数 | 含义 |
|------|---------|------|
| 已映射 | ≥5 | 评分点已找到对应章节 |
| 建议映射 | 2-4 | 评分点可能有对应章节，建议人工确认 |
| 未映射 | <2 | 评分点未找到对应章节，需检查大纲 |

### 字数分配表

根据评分分值和用户指定的目标页数自动计算各章节字数：

- 计算公式：`目标字数 = 评分分值 × (总页数 ÷ 总分) × 780`
- 合格范围：`目标 × 0.75 ~ 1.25`
- 价格类评分项不参与字数分配
- 商务类评分项标注"归属商务标，不在技术标中展开"

### 客观题与主观题分类

eval_mapping.py 自动识别评分项类型：

| 类型 | 识别关键词 | 处理方式 |
|------|-----------|---------|
| 客观题 | 资质、营业执照、证书、许可证等 | 标注为通过/不通过项，不参与字数分配 |
| 主观题 | 技术方案、项目理解、实施方案等 | 参与字数分配，需在对应章节展开 |
| 价格题 | 报价、下浮率等 | 排除字数分配，标注为价格项 |

## 模板适配（核心功能）

### 工作方式

1. 用户提供 Word 模板文件（.docx）
2. `template_extractor.py` 自动提取模板格式参数
3. `convert_to_word.py --template <模板.docx>` 基于模板生成最终文档

### 模板格式提取

```bash
python scripts/template_extractor.py <模板.docx> [输出.json]
```

提取内容：页面设置、Normal 样式、Heading 1-9 样式、正文样式、表格样式。

### 格式优先级

1. 命令行参数覆盖（`--font`、`--body-size`、`--line-spacing`）
2. 模板样式提取（`正文1` > `Normal`；`Heading 1-9`）
3. Markdown 顶部 `doc-format` 注释块
4. 默认值（宋体12pt / 1.5倍行距 / 上下2.54cm / 左右3.17cm）

### 转换命令

```bash
# 基于模板生成（推荐）
python scripts/convert_to_word.py <输入.md> <输出.docx> --template <模板.docx>

# 无模板
python scripts/convert_to_word.py <输入.md> <输出.docx>
```

### ★ 自动编号注入

**问题**：模板的 `numbering.xml` 中定义了多级编号（numId=1），但 Heading 样式未关联 numPr，导致生成的 Word 标题不显示自动编号。

**解决方案**：`convert_to_word.py` 在每个标题段落级别注入 `<w:numPr>`：
- H1 → ilvl=0（显示 1, 2, 3...）
- H2 → ilvl=1（显示 1.1, 1.2...）
- H3 → ilvl=2（显示 1.1.1, 1.1.2...）

注入逻辑会检查样式级别是否已有 numPr，避免重复注入。如果模板样式已正确关联编号，则跳过段落级注入。

## 内容编写规则

### 基本规则

| 规则 | 说明 |
|------|------|
| 段落结构 | 每小节（`### X.X.X`）≥ 3 个独立段落，禁止单一长段落 |
| 表格展示 | 用户选择添加表格图表时，每个 H2 章节至少包含 1 个表格或图表描述；未选择时不强制 |
| 禁用词汇 | 不用"我方/我们"；用"将/项目组/本方案" |
| 金额描述 | 禁止在技术标中出现金额/预算描述 |
| 内容贴合 | 严格按评分标准和采购需求编写，不泛泛而谈 |
| 章节结尾 | 禁止写「本章小结」「本章总结」等；正文写完即结束 |
| 章节序号 | 统一使用中文数字（一、二、三…），禁止混用阿拉伯数字 |

### 内容强相关要求

1. **逐条响应**：评分标准中每个评分点必须在对应章节中直接回应
2. **引用需求**：引用招标文件中的具体需求条款编号或原文
3. **针对性方案**：方案内容必须针对该项目具体情况，不可用通用模板套话
4. **项目名称**：正文中必须使用招标文件中的准确项目名称
5. **技术参数**：涉及技术指标时，必须与招标文件要求对齐，不可编造

## 正文表格与图表编写指南

当用户在步骤②选择「添加表格图表」时，编写各章节正文须在适当位置插入表格和图表描述，丰富内容呈现。

### 插入原则

| 原则 | 说明 |
|------|------|
| 因章制宜 | 不同章节类型插入不同类型的表格/图表，不可千篇一律 |
| 适度插入 | 每个 H2 章节至少 1 个表格或图表描述，不宜过多（不超过 3 个） |
| 内容相关 | 表格/图表内容必须与招标文件需求和评分标准强相关，不可填充无关内容 |
| 数据真实 | 表格中的技术参数、指标数据必须与招标文件对齐，不可编造 |
| Markdown 格式 | 表格使用 Markdown 管道表格语法，convert_to_word.py 自动转为 Word 表格 |

### 各章节类型推荐表格/图表

| 章节类型 | 推荐表格 | 推荐图表描述 | 说明 |
|---------|---------|------------|------|
| 项目理解/背景 | 项目需求梳理表、建设现状对比表 | — | 梳理招标文件中的核心需求点 |
| 技术方案 | 技术架构分层表、技术选型对比表 | 系统架构图（文字描述）、数据流程图（文字描述） | 技术选型对比表列出候选方案优劣 |
| 实施方案/进度 | 里程碑计划表、人员投入表、甘特图数据表 | 实施进度甘特图（文字描述） | 里程碑表含阶段、时间、交付物 |
| 售后服务 | 服务响应级别表、SLA 指标表 | 服务流程图（文字描述） | SLA 表含响应时间、解决时间、升级路径 |
| 培训方案 | 培训课程表、培训对象与内容对照表 | — | 课程表含课程名、课时、对象、方式 |
| 安全规划 | 安全措施对照表、等保要求映射表 | 安全防护架构图（文字描述） | 等保映射表对照等保要求与实施方案 |
| 风险评估 | 风险矩阵表、风险应对计划表 | 风险等级分布图（文字描述） | 风险矩阵含风险项、概率、影响、应对 |
| 质量管理 | 质量控制点表、质量指标表 | 质量管控流程图（文字描述） | 控制点表含阶段、控制项、标准、责任人 |
| 团队管理 | 人员配置表、岗位职责表 | 组织架构图（文字描述） | 人员配置表含角色、人数、资质要求 |
| 验收方案 | 验收标准表、验收流程表 | 验收流程图（文字描述） | 验收标准表对照招标文件验收要求 |

### 表格编写规范

1. **表头明确**：每列有清晰的列标题，不可含糊
2. **行列完整**：表格行数 ≥ 3（不含表头），列数 3-6 列为宜
3. **数据具体**：表格内容用具体数据或明确描述，不可填「等」「详见正文」
4. **与正文衔接**：表格前后须有引导句和说明句，不可孤立出现
5. **Markdown 语法**：使用标准管道表格 `| 列1 | 列2 |`，convert_to_word.py 自动转换
6. **表格格式独立于正文**：convert_to_word.py 在转换表格时，字体字号与模板正文一致，但段落格式（首行缩进、行距、段前段后间距）独立设置——单元格首行缩进归零、行距为单倍行距、段前段后为 0pt，避免被 Normal 样式的正文段落格式带偏导致表格内容错位

示例：

```markdown
本项目实施进度里程碑计划如下表所示：

| 阶段 | 里程碑 | 时间节点 | 主要交付物 |
|------|--------|---------|-----------|
| 启动阶段 | 项目启动会 | 合同签订后5个工作日 | 项目启动报告、实施计划 |
| 需求阶段 | 需求确认 | 启动后15个工作日 | 需求规格说明书 |
| 开发阶段 | 系统初验 | 需求确认后60个工作日 | 系统初验报告、用户手册 |
| 试运行 | 试运行结束 | 初验后30天 | 试运行报告 |
| 终验 | 项目终验 | 试运行结束后10个工作日 | 终验报告 |

上表中各阶段时间节点根据招标文件服务期要求倒排，确保整体进度可控。
```

### 图表描述编写规范

由于 Markdown → Word 转换不生成实际图片，图表以**文字描述+表格数据**形式呈现：

1. **图表标题**：用 `**图表：XXX**` 标注
2. **图表说明**：描述图表类型（流程图/架构图/甘特图等）和展示内容
3. **数据表格**：将图表数据用表格形式列出
4. **分析说明**：表格后附 1-2 句分析说明

示例：

```markdown
**图表：系统部署架构图**

本系统采用分层部署架构，各层组件及部署关系如下表所示：

| 层级 | 组件 | 部署位置 | 主要功能 |
|------|------|---------|---------|
| 接入层 | 负载均衡器 | DMZ区 | 流量分发、SSL卸载 |
| 应用层 | 应用服务器集群 | 应用区 | 业务逻辑处理 |
| 数据层 | 数据库集群 | 数据区 | 数据存储与备份 |
| 管理层 | 运维管理平台 | 管理区 | 监控告警、日志分析 |

各层之间通过防火墙策略隔离，仅开放必要端口，确保系统安全性。
```

### 不添加表格图表时的处理

用户选择「不添加」时：
- 正文以纯文字段落为主
- 仍可保留少量必要的表格（如评分标准要求表格展示的内容）
- 不强制插入图表描述
- token 消耗按基准值计算

## 去 AI 痕迹（必须执行）

章节编写完成后，必须执行去 AI 痕迹处理。

### 参考文件

| 文件 | 用途 |
|------|------|
| `references/de-ai-rules.md` | 速查规则：红旗词词典、结构去模式化、语气自然化、标书专项检查 |
| `references/humanizer-zh.md` | 完整理论指南：24 种 AI 写作模式详解与改写示例 |

### 处理步骤

1. **红旗词扫描** — 查找替换高频 AI 词汇（此外、值得注意的是、不仅...而且等）
2. **结构去模式化** — 打破对称列表、对称段落、从句配对
3. **语气自然化** — 缩短句子、口语化表达、变化节奏、使用具体数据
4. **标书专项检查** — 金额/预算、人称代词、章节总结、通用积极结论
5. **★ 组合词检测** — 简单替换可能产生生硬组合词，必须检查上下文
6. **默读检验** — 读起来像能干的同事写的就对了

### ★ 上下文感知替换策略

**禁止盲目全局替换**。同义词替换时必须考虑上下文，否则会产生生硬的组合词。

教训案例：将「闭环」统一替换为「完整处置」后，产生了 47 处异常组合：
- `闭环安全处置` → `完整处置安全处置`（重复冗余）
- `闭环管理` → `完整处置管理`（不自然）
- `闭环跟踪` → `完整处置跟踪`（不自然）
- `完整闭环` → `完整完整处置`（叠词错误）

正确做法 — **按上下文分场景替换**：

| 原始词 | 上下文场景 | 正确替换 | 错误替换 |
|--------|-----------|---------|---------|
| 闭环 | 闭环管理 | 全过程管理 | ❌ 完整处置管理 |
| 闭环 | 闭环跟踪 | 全过程跟踪 | ❌ 完整处置跟踪 |
| 闭环 | 闭环安全处置 | 安全处置全流程 | ❌ 完整处置安全处置 |
| 闭环 | 闭环率 | 处置完成率 | ❌ 完整处置率 |
| 闭环 | 闭环性 | 完整性 | ❌ 完整处置性 |
| 闭环 | 闭环管控 | 全程管控 | ❌ 完整处置管控 |
| 闭环 | 闭环确认 | 最终确认 | ❌ 完整处置确认 |
| 闭环 | 闭环化验证 | 体系化验证 | ❌ 完整处置化验证 |

替换后必须执行**组合词扫描**，检查是否产生新的生硬组合：

```bash
# 扫描替换后的文件，查找异常组合
python -c "
import re
with open('合并稿.md', 'r', encoding='utf-8') as f:
    c = f.read()
# 检查重复词：如 XX完整处置XX、完整完整等
for pattern in [r'(.{2})\\1', r'完整处置.{0,3}完整处置', r'完整完整']:
    for m in re.finditer(pattern, c):
        print(f'  异常组合: {m.group()}')
"
```

### 标书专项禁止项

- 任何金额/预算/报价描述
- "我方/我们"人称（用"将/项目组/本方案"）
- "本章小结/总结"等总结段
- "未来光明""激动人心""迈向新台阶"等通用积极结论
- "从X到Y"虚假范围
- "标志着""见证了""彰显了"等夸大象征意义

## 方案片段库（memory）— 编写加速核心

### 原理

标书有大量通用章节（风险评估、项目管理、开发过程管理、安全规划等），内容结构和方法论高度相似。
片段库将这些通用内容预存，写新标书时**直接抽取 → 根据项目信息改写**，跳过从零思考的环节。

### memory 目录结构

路径由 config.json 的 `memory_path` 决定（首次配置时自动创建）：

```
{桌面}/{memory名称}/memory/     ← memory_path
├── snippets/                    # 通用方案片段
│   ├── 风险评估/                # 按章节类别分目录（首次配置按行业自动创建）
│   │   ├── index.json          # 片段索引
│   │   ├── *_完整.md           # 完整方案
│   │   ├── chapters/           # ## 级章节片段
│   │   └── sections/           # ### 级小节片段
│   ├── 项目管理/
│   ├── 开发过程管理/
│   ├── 安全规划/
│   └── ...
├── outlines/                    # 大纲模板（按项目类型）
│   ├── 信息化项目/
│   ├── 安全规划项目/
│   └── ...
├── vocabulary/                  # 行业术语/标准引用（首次配置自动生成种子）
│   └── 术语表.md
└── projects/                    # 历史项目索引
```

> 所有脚本中引用 memory 路径时，从 config.json 的 `memory_path` 读取，不硬编码。

### 使用命令

```bash
# 完成标书后 → 抽取通用片段存入 memory
python scripts/snippet_manager.py save <完成的方案.md> --category 风险评估

# 开始新标书 → 搜索相关片段
python scripts/snippet_manager.py search 风险预警

# 加载片段 → 基于片段改写
python scripts/snippet_manager.py load 风险评估/风险监控 --output 新项目_风险监控.md

# 合并多个片段 → 组合草稿
python scripts/snippet_manager.py merge 风险评估/风险识别 风险评估/风险分析 --output 草稿.md

# 查看已有片段
python scripts/snippet_manager.py list
python scripts/snippet_manager.py list --category 风险评估
```

### 片段适配检查（必须执行）

**从片段库加载并改写片段后，必须运行适配检查，确保原项目的专属字眼不会泄露到新标书中。**

片段中可能残留的专属字眼类型：
- **公司名**：贵州泰若数字科技有限公司、中电福富信息科技有限公司 等
- **系统名**：4G统一DPI系统、业务运营平台、漏洞管理平台 等
- **项目名**：4GDPI维保、流动数据安全能力提升 等
- **人员姓名**：标书中出现的个人姓名
- **招标方**：中国电信贵州公司、天翼视联 等

```bash
# 检查单个改写后的片段是否有残留
python scripts/snippet_adapt.py check <改写后的文件.md> --project "当前项目名" --company "当前公司名" --system "当前系统名"

# 批量检查某个目录下所有片段
python scripts/snippet_adapt.py batch <目录> --project "当前项目名" --company "当前公司名" --system "当前系统名"

# 自动替换残留字眼（提供替换映射）
python scripts/snippet_adapt.py adapt <文件.md> --mapping '{"4G统一DPI系统": "漏洞管理平台", "4GDPI维保": "漏洞管理平台运营"}' --output 输出.md
```

**执行规则：**
1. 步骤⑨中每加载一个片段改写完成后，立即运行 `snippet_adapt.py check` 验证
2. 如果发现残留字眼，必须通过 `adapt` 替换或手动改写，直到 `check` 通过（显示 `✓ 未发现原项目专属字眼`）
3. 步骤⑬汇总整合后，对最终合并稿运行一次全量 `check`，确保零残留
4. `--project`、`--company`、`--system` 三个参数用于排除当前项目自身的名称（不算残留）

### 片段相关性预筛（必须执行）

**字眼替换只是表面，内容本身必须与招标项目实质相关。** 一个来自4GDPI维保项目的巡检片段（机房温湿度、分光器端口检查），即使系统名替换成了漏洞管理平台，内容本质与漏洞管理毫无关系。

相关性检查通过三个维度评分：
- **片段关键词相关占比**（50%）：片段中的关键词有多少出现在招标文件中
- **核心词匹配率**（30%）：招标文件高频核心词与片段的重合度
- **招标关键词覆盖率**（20%）：片段覆盖了多少招标文件关键词
- **跨领域污染惩罚**：片段中大量出现某领域概念但招标文件中没有（如电信运维概念出现在安全项目中）

评分等级：
| 等级 | 分数 | 含义 | 处理方式 |
|------|------|------|----------|
| 高 | ≥60 | 片段内容与项目高度相关 | 可直接改写使用 |
| 中 | 35-59 | 部分相关，有可复用框架 | 需大幅改写，删除不相关内容，补充项目特定内容 |
| 低 | <35 | 内容与项目基本无关 | 弃用，从零编写 |

```bash
# 检查单个片段与招标文件的相关性
python scripts/relevance_check.py check <片段.md> --tender <招标文件解析结果.md> --project "当前项目名"

# 批量检查目录下所有片段
python scripts/relevance_check.py check-dir <片段目录> --tender <招标文件解析结果.md> --project "当前项目名"
```

**执行规则：**
1. 步骤⑦搜索片段后、步骤⑨改写前，对每个候选片段运行 `relevance_check.py check`
2. 低分片段（<35）直接弃用，不进入改写流程
3. 中等片段（35-59）改写时须删除不相关内容，仅保留可复用的框架结构
4. 步骤⑬汇总整合后，对最终合并稿运行全量相关性检查，确保无跨领域污染

### 加速策略

| 策略 | 效果 | 实现方式 |
|------|------|---------|
| 片段预填充 | 通用章节从70%完成度开始改写，而非从零写 | snippet_manager search → relevance check → load → adapt check → 改写 |
| 大纲模板 | 跳过大纲设计环节，直接使用历史大纲微调 | outlines/ 目录预设大纲 |
| 评分点自动映射 | 解析评分标准后自动映射到各章节，生成覆盖检查报告和字数分配表 | eval_mapping.py report 一步生成映射表+覆盖检查+字数分配 |
| **必含标题检测** | 自动提取「包括但不限于」枚举项，确保 H2 全覆盖 | eval_required_headings.py report |
| **Token/时间估算** | 大纲确认时预知 token 用量和编写耗时 | estimate_tokens.py estimate |
| 并发章节编写 | 多章节同时编写，总耗时从 Σ 降低到 max | Task 工具并发调用 |
| 模板一次适配 | 首次使用模板提取格式参数，后续直接复用 JSON | template_extractor.py 输出缓存 |

## 文档质量全检查（生成后必须执行）

生成 Word 文档后，必须运行质量检查脚本：

```bash
python scripts/doc_quality_check.py <输出.docx> --template <模板.docx>
```

### 检查维度

| 维度 | 检查内容 | 严重度 |
|------|---------|--------|
| 字体 | 正文/标题是否使用了非预期字体 | 警告 |
| 段落格式 | 行距、首行缩进、段前段后间距 | 警告 |
| 编号冗余 | 标题中残留编号文本（与模板自动编号冲突） | 错误 |
| 编号冗余 | Heading 段落级 numPr 重复 | 警告 |
| Heading 冗余 | run 级字号/加粗覆盖样式定义 | 警告 |
| AIGC 水印 | 系统注入的 UUID 水印（隐藏文本） | 正常（info） |
| AIGC 痕迹 | AI 声明文本（"AI生成"等） | 错误 |
| AIGC 痕迹 | python-docx 生成痕迹 | 警告 |
| AIGC 痕迹 | AI 高频填充词/夸大表达/通用套话 | 警告 |

### AIGC 标识检查详情

检查脚本会扫描以下 AIGC 标识类别：

| 类别 | 示例 | 严重度 |
|------|------|--------|
| 系统水印 | `AIGC标识: <UUID>`（隐藏文本 + docProps/custom.xml） | 正常（info） |
| 声明文本 | "AI生成" "AI撰写" "人工智能生成" | 错误 |
| 生成工具 | "python-docx" "generated by python" | 警告 |
| AI 特征词 | "值得注意的是" "不言而喻" "毋庸置疑" | 警告 |
| AI 结构模式 | "不仅…而且…还…" 对称从句 | 警告 |
| AI 夸大表达 | "标志着" "见证了" "迈向新台阶" | 警告 |
| AI 煽情表达 | "未来光明" "砥砺前行" "乘风破浪" | 警告 |
| 通用套话 | "将为…带来提升" "实现跨越式发展" | 警告 |

#### ★ AIGC 水印系统行为说明

**系统会自动向 `.docx` 文件注入 AIGC 水印，这是合规要求，不可删除。** 具体注入位置：

| 注入位置 | 内容 | 格式 |
|---------|------|------|
| `word/document.xml` 末尾 | `AIGC标识: <UUID>` | 隐藏文本（`<w:vanish/>`），字号 8pt，灰色 BFBFBF |
| `docProps/custom.xml` | `AIGC` 自定义属性 | JSON 格式，含 ContentProducer/ProduceID/Label 等字段 |

**处理策略：**
1. `convert_to_word.py` 的 `_fix_docx_metadata()` 函数已清理 `python-docx` 痕迹和元数据
2. AIGC 水印由系统钩子在文件创建/修改后自动注入，**脚本层面无法删除**（删除后钩子会重新注入）
3. 隐藏文本水印（`<w:vanish/>`）在 Word 中默认不可见，不影响正常阅读和打印
4. `docProps/custom.xml` 中的 AIGC 属性不影响文档内容，仅在文件属性面板中可见
5. 质量检查脚本检测到 AIGC 水印时标注为「系统注入（正常）」，不视为质量问题
6. 如用户询问 AIGC 标识，直接说明：这是系统合规水印，自动注入，不可删除
