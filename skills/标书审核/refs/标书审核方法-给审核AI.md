# 标书审核方法（给审核 AI）

本手册从 2026 年云网运营账号集约管理技术服务项目的 Grok Build 互审实践抽出。适用对象：另一套审核 AI。任务是**对照招标文件审投标文件**，不是改标、不是写标。

项目路径（本轮实例）：`D:\文件同步\售前\2026云网账号集约管理技术服务`  
历次产出：`审核输出/` 下亿讯 / 鸿信 / 福富技术册、鸿信商务册。

---

## 0. 角色与边界

你是评委视角的互审员，不是投标文件作者。

**做：**

- 对照招标文件找硬伤、漏项、自相矛盾、格式错、给分风险
- 每条问题必须能被 Word `Ctrl+F` 复核
- 区分：资格（过/不过）≠ 评分（给多少分）≠ 观感（编制分）
- 用户声明「人员后补 / 本轮不审商务」时，**内容空不算问题，表结构错仍要报**

**不做：**

- 用户没要求就不要改 Word
- 不要用「建议进一步完善」「整体较好」这类空话代替条目
- 不要发明招标没有的评分规则
- 不要把商务册的问题写进技术册清单（可交叉提示「见商务册」）
- 须知前附表与正文冲突时，**以前附表为准**（本项目 3.2.2 偏离表应答「全部满足」压过第六章「空表视为满足」）

## 1. 开工必读（不读完不准出清单）

按这个顺序打开，不要先翻投标文件：

| 顺序 | 文件 | 抽出什么 |
|------|------|----------|
| 1 | 招标文件 + 须知前附表 | 项目名、编号、是否划分标包、投标截止、有效期、保证金、签字盖章、3.1 / 3.2.2、服务期 |
| 2 | 附件1 评标办法 | 初步评审（形式/资格/响应性）逐条；详细评审每个评分点的**原文公式、注、不得分条件** |
| 3 | 附件2 商务规范书 | 合同服务期、付款、考核、承诺书必填空（如信息安全责任人） |
| 4 | 附件3 技术规范书 | 技术建议书必含章节；功能清单（2.4 等）；培训/考核/角色原文；有无 ★ |
| 5 | 第六章格式 + 附件4 表格 | 封面、索引表列、偏离表列名、表一～表六字段。**模板缺序号 4 就保留缺 4，不要自行改成 1–7** |

读完在脑中固定四个数（本项目实例，换项目就重填）：

- 投标截止：2026-09-03
- 服务期：合同签订之日至 2026-12-31 → 实际大约 15–16 周
- 技术 50 + 商务 10 + 价格 40
- 同类业绩窗口：2023-07-01 至招标公告发布日；同类 = 4A / 零信任 / 账号管理平台 / 身份认证，且是**开发实施**不是纯运维

## 2. 审核流程

```
读招标四件套
    → 抽出评分点公式 + 规范书必含项 + 格式表样
    → 抽投标文件全文（段落 + 全部表格 + 图片 OCR）
    → 先形式/模板，再规范书覆盖，再评分点打分，再一致性/造假观感
    → 输出互审意见 md（见第 3 节格式）
    → 若是改稿复核：先对上一轮每条做「已改 / 部分改 / 未改 / 回潮」
```

抽取要求：

- 表格必须整表抽出，不要只看标题
- 证书、合同、身份证、营业执照、开户许可**要看图，不要只信表里的字**
- 页码会漂，**定位靠关键字**；页码只作参考
- 同一词会命中索引表和正文：写明「第几次命中 / 避开索引」

## 3. 强制输出格式

输出一份 Markdown，放到 `审核输出/`。文件名：

`{商务|技术}投标文件互审意见-{投标人}-{分册}[可选-复核|终评].md`

### 3.1 文首元数据（每份都要）

```
# {商务|技术}投标文件互审意见（{投标人}·{分册}）

**项目名称**：…
**招标编号**：…
**被审文件**：路径 + 约 xx 页 + 文件日期
**对照文件**：附件1 / 2 / 3 / 招标须知前附表 / 第六章格式（写明本轮用了哪几份）
**本轮不审**：用户划出的范围（如商务册、人员证件）
**审核日期**：…
**证件**：是否逐张 OCR（没做就写没做）
```

紧跟一段「怎么用」：

> Word 打开投标文件，`Ctrl+F` 搜「定位关键字」。页码会漂，以关键字为准。  
> 「全文无命中」= 功能/章节缺失。  
> 复核稿要写「怎么搜验证」。

### 3.2 一、总判断（先给结论）

用 3～5 条硬的，不要先夸再骂。每条对应后面的 A/B 号。终评稿还要给分数区间。

### 3.3 二、问题清单（检查清单主体）

分级，不要按章节流水账：

| 级 | 含义 | 典型 |
|----|------|------|
| **A 必须改** | 否决 / 资格不过 / 评分公式直接归零 / 服务期不可行 | 授权书空、成立时间写错、进度排不进服务期、改写考核办法、贴错索引表 |
| **B 规范书漏项 / 正文打架** | 实施方案完整性、自相矛盾 | 查询统计无检索维度、人脸协议 REST vs gRPC、客户经理角色缺失 |
| **C 模板 / 编制** | 编制情况 2 分、评委检索 | 索引空、……未删、封面空、额外承诺 `1. 2.`、交叉引用幽灵章节 |
| **D 人员 / 证明格式** | 后补前必须先改表；内容可空 | 表五姓名列填了岗位、履历不是表六、自拟知识产权清单 |

**问题表列（技术/商务通用，按此列，不要改列名）：**

| 列 | 要求 |
|----|------|
| 号 | A1 / B1 / C1… 本轮稳定编号。合并别人清单时加「原号」列 |
| 问题 | 一句话说完，**加粗关键事实** |
| 参考页 | 大约页，标明会漂 |
| 定位关键字 | 可直接粘贴进 Word 的短词，用反引号。多词用 `；` |
| 命中 | 第几次 / 无命中 / 在哪一节。避免「全文搜到很多次」这种废信息 |
| 影响与整改 | 对应哪条招标原文 + 怎么改才算过。不要只写「建议补充」 |

复核稿额外一张闭环表：

| 原号 | 问题 | 结果（已改/部分改/未改/回潮） | 怎么搜验证（期望命中或应为 0） |

终评稿额外一张给分表，见第 5 节。

### 3.4 三、覆盖对照表（技术册必做）

规范书条款 × 判定（✅ / ⚠️ / ✗）× 怎么搜。  
「有章节名但没写规范书原词」算 ⚠️，不是 ✅。

### 3.5 文末可写「核对后建议不改」

例如索引表缺序号 4 是招标模板原文，不要当成问题。这能避免用户按错误批注去改。

## 4. 检查点总表

下列是本项目打磨出的稳定检查点。换项目时**公式按新招标替换，检查类别保留**。

### 4.1 形式 / 资格（不过就进不了详细评审）

| 检查点 | 怎么查 | 本项目教训 |
|--------|--------|------------|
| 投标人名称 = 营业执照 | 封面、投标函、执照图 | — |
| 投标函项目名、编号、有效期 | 对照前附表 | 残留 `【招标人名称】`、`/ 标包` |
| 保证金 | 前附表「无需」则填 `/` 即可 | 不要当成漏填 |
| 授权委托书 | 有标题就要有正文，或明确「法定代表人亲自投标、不涉及」 | 鸿信商务册标题后直接跳到廉洁承诺 |
| 法定代表人身份证明 | 成立时间、姓名、身份证正反面扫描件 | 写成 **2027** 年（执照是 2007） |
| 签字盖章 | 电子标看 CA；Word 仍要有落款位置 | — |
| 资格业绩 | 窗口期内 ≥1 个同类**开发实施**合同，关键页：标的、金额、盖章 | 运维合同不能撑资格（但有其他开发合同即可过） |
| 联合体 / 代理商 | 承诺函 | — |
| 不得存在的情形 | 裁判文书网、失信被执行人、信用中国 | 截图账号/日期不统一；用了执行网代替信用中国 |
| 投标有效期 | 投标函天数 | 本项目 120 天 |

### 4.2 编制与模板（编制情况 2 分）

| 检查点 | 怎么查 |
|--------|--------|
| 用对索引表 | 技术册必须是「案例与业绩 / 团队 / 知识产权 / 实施方案 / 开发过程 / 服务方案」，**不是**初步评审 15 行（鸿信贴错过） |
| 索引页码 | 排版后回填；商务内容写「见商务册第××页」；删 `……` |
| 封面 | 项目全称、不划分标包、投标人、日期 |
| 偏离表 | 列名必须是招标原列：序号 / 招标文件条目号 / 招标文件的技术（或合同）条款 / 投标文件偏离情况 / 说明。表上要有项目名称、编号、标包（不划分填 `/`）。至少一行「全部满足」或「无偏离」 |
| 目录对齐评分点 | 技术建议书要能搜到：`1、实施方案` `1.1、开发方案` … `1.6、进度流程控制` `2、开发过程管理方案` `3、服务方案`。自拟「第一～四部分」评委对不上分 |
| 额外服务承诺 / 其他相关文件 | 不许只剩 `1. 2.`。承诺要可量化增值，不要复述规范书义务。其他文件按规范书点名手册并指向章节 |
| 编制要求、【】占位、示例、XX年 | 正式稿必须清掉 |
| 交叉引用 | `12.1节` `第九章` `表14-x` 若目录已改，即幽灵引用 |
| 四级标题灌水 | 同一骨架复制 N 个模块（鸿信标题4 曾 393 个）。编制分和「针对性」都吃亏 |

### 4.3 技术规范书应答（实施方案 4 分的骨架）

**结构必含（附件3 原文）：** 总体技术方案、设计原则、方案优势、优化设计思路。  
**评分点六块：** 开发、测试、集成部署、应急保障、质量管理、进度流程控制。  
**开发过程：** 需求计划、项目组织、交付。  
**服务：** 保障、风险、保密；另加培训（目的/内容/流程/课程）、技术支持。

功能覆盖用**规范书原词**搜，不要用同义改写蒙混：

| 必搜原词 | 漏了会发生什么 |
|----------|----------------|
| `查询统计` `快速过滤器` `资产IP` `有效期范围` | 有「高级查询」四字仍算漏 |
| `非人员账号` `收藏夹` `标签化` `禁止人员直接登录非人员账号` + 拦截 | 只写采集不算完整 |
| `超级管理员` 等数据处理五类角色 | 只在测试范围点名不算 |
| `资源管理` | 功能开发表要有独立行 |
| `客户经理` | 考核总体要求：项目经理**和**客户经理。人员可后补，方案角色不能缺 |
| `运行安全管理平台`（人脸结果外发） | 写成「监管平台」即对象错误 |
| `培训目的` | 写成「培训目标」会被抠字 |
| `金库` `字符堡垒` `图形堡垒` `数据库堡垒` `主机堡垒` `环境感知` | 写在测试/配置、开发方案没有，完整性扣分 |
| 考核原文：完成 60 / 进度 10 / 文档每次扣 1 / 满意度 10 / 网信安通报每次扣 3 | **禁止自拟权重**（可用性 20% 这类） |

**自相矛盾专项：**

- 同一接口两处协议不同（人脸 HTTPS/REST vs gRPC；监管数字证书 vs Syslog+Kafka）
- 多套工期（13 周上线 / 18 周终验 / 26 周 / 44 周 / 2026-01-01 开工）
- SLA 多套（30 分钟 vs 2 小时 vs 4 小时），对外只留一套并对应考核
- 人数口径（表五 12 人 vs 服务方案 18 人 vs 「不少于 10 人」）
- 性能指标标注「来源：技术规范书」但规范书没有该数字 → 改为「投标人建议指标」

**进度铁律：** 用投标截止倒推服务期，计划总周数必须能进截止日期。甘特图年份/月份必须对得上，不能拿年初模板。

### 4.4 评分点打分（详细评审）

先抄公式，再套材料。**未提供扫描件不得分** 的项，空节=0，不要打同情分。

**技术 50（本项目）：**

| 点 | 分 | 计分要点 |
|----|----|----------|
| 业绩-数量 | 8 | 资格 1 个不计分；每多 1 个同类 +2。必须开发实施 |
| 业绩-金额 | 10 | 同类累计 ≥100 万后，每 +30 万 +1。**同一合同不能既计数量又计金额**；未注明类别则先数量后金额 |
| 项目经理+技术经理 | 10 | 必须两人；工作经验从毕业起算；硕士；PMP/高项/中项任一本；技术经理信息化/IT 服务证书。要身份证、学历、证书、履历、近半年连续 3 个月社保（缴费单位=投标人）或劳动合同 |
| 成员配置 | 8 | 岗位覆盖最多 4：需求/架构/前后端/移动/测试/安全。数量：不含两名经理 ≥10 人，每多 1 人 +1、最多 +4。正好 10 人则数量加分 0 |
| 知识产权 | 4 | 账号安全 / 运维审计 / 权限管控，每项 1 分。必须是**投标人**的有效证书扫描件。公车监管、5G 核心网运维等弱相关可能 0 |
| 实施方案 | 4 | 完整全面、针对、可行；(3,4] / (2,3] / (1,2] / (0,1]，步长 0.1 |
| 开发过程 | 3 | 同上档 |
| 服务方案 | 3 | 同上档 |

**商务 10：**

| 点 | 分 | 计分要点 |
|----|----|----------|
| 企业整体实力 | 6 | 七选六，每证 1 分：信息安全服务（安全开发或数据安全类）、CMMI、DCMM、ISO20000、ISO27001、ISO9001、ISO45001。看有效期和扫描件，表名写成套话也要能对上证 |
| 商务条款满足 | 2 | 全部满足满分，每项不满足 -1。承诺书必填空空白可能被算一项不满足 |
| 编制情况 | 2 | 优秀 (1,2]；一般 (0,1] |

**价格 40** 本审核默认不评，除非用户给报价文件。

### 4.5 人员与证明

| 检查点 | 说明 |
|--------|------|
| 表五字段 | 序号、团队角色、姓名、学历、专业、同类年限、证书、证明页码。角色列=岗位，姓名列=人名 |
| 表六字段 | 招标原列；工作经历要多行，不能压成一行 |
| 经理 ≠ 技术经理 | 同一人该项不得分 |
| 履历时间 | 禁止写未中标的「本项目、2026年1月至今」。用可核验的历史项目，时间错开 |
| 履历套话 | 删末行「…」；第 2、3 条不要全员同一句 |
| 社保 | 缴费单位必须是投标人；框选不要误框别人 |
| 证件页码 | 表五末列要能翻到对应扫描件 |
| 专业匹配 | 生物电子学做移动端、工商管理做安全，不一定扣，但要能解释 |
| 承诺人数 | 正文「不少于 10 人、覆盖 6 岗」必须和表五一致 |

### 4.6 业绩与知识产权（常在商务册、分在技术）

**合同三页：** 标的内容页、金额页、盖章页。缺一页评委可不认。框架合同还要订单/结算单。

**表四：**

- 每条备注必须写「案例与业绩-数量」或「案例与业绩-金额」
- 「产品及服务内容」不要写「同类项目案例」，写「零信任系统开发实施」等可核对短句
- 填证明页码、合计金额、用户电话（禁止 `/`）
- 货物合同若名称含零信任，备注里点出系统/集成部分，避免被当成纯供货
- 维护/年度运维合同：资格和评分都要开发实施，**高风险剔除**

**软著/专利：**

- 著作权人 = 现投标人名称，或同一信用代码曾用名 + 工商变更页
- 主题必须落在三类：账号安全、运维审计、权限管控
- 技术册不要自拟「知识产权证明」清单表；只附扫描件
- 技术册空节但商务册有证：两边索引互指页码，否则技术分仍按未提供

### 4.7 商务其它

| 检查点 | 说明 |
|--------|------|
| 表一 vs 表二 vs 开户许可 | 基本账户必须同一账号（鸿信表一 `…000` 与许可证 `…588` 不一致） |
| 邮编 / 地址 / 法人 | 投标函与表一、执照一致 |
| 控股表 | 填完后删 `【投标人名称】` 模板括号 |
| 特定关系 | 不涉及就填「不涉及」，不要再附一份正文写「我方存在相关情形」的承诺函 |
| 投标专用章 | 不涉及只留一句，删空白模板 |
| 网安承诺书责任人 | 姓名、职务、联系方式必填 |
| 软件成分清单 | 空表 + 「100% 自主编写」要能自圆；技术册若出现开源框架，收窄承诺范围 |
| 一般纳税人证明 | 过旧（如 2020 年）降观感，通常不否 |

### 4.8 一致性 / 造假观感

- 全员履历同一项目同一起止日期
- 声称 17 年经验履历只列 2 个近一年项目
- 证书有效期、发证机构与表三不一致
- 「来源：技术规范书」但规范书无此句
- 风险表标注「（示例）」

### 4.9 AI / 制作痕迹（发现即 A 级）

| 痕迹 | 怎么查 |
|------|--------|
| 隐藏 AIGC 标识、custom.xml | 文末 vanish 文字、文档属性 |

## 5. 给分方法

1. 先抄招标公式，再填材料。
2. 步长 0.1；写区间时给中位。
3. 客观项（证书、人数、业绩）能算就不要估。
4. 主观项（方案 4/3/3）用档：完整针对可行偏上打档顶附近，缺块或矛盾降一档。
5. 「未提供不得分」= 0，不要 0.5。
6. 本册没有的材料标「未评，见××册」，不要用另一册的想象分填进来。
7. 终评给一张拼图：

```
商务 10     = 实力 + 条款 + 编制
技术 50     = 业绩18 + 经理10 + 成员8 + 知产4 + 方案4+3+3
本册能定的  单独小计
乐观/中位/悲观 三行
```

8. 同时指出**还能抢的分**（补 4 人、补 4 本软著、补金额类合同），方便用户决策，不要只报忧。

## 6. 复核轮次怎么做

用户说「改完再看」时：

1. 打开上一份互审意见，对 A/B/C/D **逐条搜验证**，不要凭印象。
2. 专门查**回潮**：索引页码又空了、额外承诺又变 `1. 2.`、1.1–1.6 编号又没了（鸿信都发生过）。
3. 新插入的材料用第 4 节再扫一遍（补人后出现「本项目 2026年1月至今」）。
4. 页码以用户插入的正式页码为准；用户若只给「成员配置在第 18 页」，用差值推算其它页，并声明算法。
5. 输出「整改复核」或「终评」，不要覆盖上一份原文，另存。

## 7. 本项目反面教材（给审核 AI 校准嗅觉）

| 现象 | 为何严重 |
|------|----------|
| 技术索引表贴成初步评审表 | 评委按评分点检索等于没编 |
| 26 周 / 44 周 / 2026-01 开工 | 服务期到 12-31，计划不可执行 |
| 考核表自拟权重 | 改甲方规则 |
| 履历写本项目尚未中标 | 弄虚作假观感 |
| 成员不含经理正好 10 人 | 数量加分公式得 0 |
| 知识产权空节或弱相关运维软著 | 注：未提供不得分 |
| 表四不标数量/金额 | 先数量后金额 → 金额 10 分变 0 |
| 运维合同当开发实施 | 资格或评分被剔 |

| 隐藏 AIGC + Mermaid 源码 | 一票否决级观感 |
| 人脸一处 REST、一处 gRPC | 评委一对就穿 |

## 8. 工作纪律

- 关键字必须是投标文件里真实存在或确实不存在的词，不要编搜不到的「智能」同义词。
- 报「无命中」之前自己先搜一遍近义词，避免把「培训目标」漏报成「没写培训」。
- 同事批注要对照加深，不要复述一句「与模板不一致」；要写清错在哪一列、应换成哪张表。
- 别人清单合并时保留「原号」，方便用户对账。
- 不要把「序号缺 4」这类模板原文当缺陷。
- 不要审报价策略、串标、压价，除非用户明确要。
- 输出给用户看：先总判断和分数，再表格；不要先倒方法论文。
- 改稿是另一任务；本手册默认只出清单。

## 9. 最小可运行提示词（可直接贴给另一审核 AI）

```
你按《标书审核方法-给审核AI的检查清单》审这一份投标文件。

项目招标文件在：{标底/确定版目录}
被审文件：{路径}
分册：技术册 / 商务册
本轮不审：{例如人员证件 / 报价}

强制：
1. 先读附件1公式、附件3必含项、第六章表样，再抽投标文件。
2. 输出必须含：元数据、怎么用、总判断、A/B/C/D 问题表（号/问题/参考页/定位关键字/命中/影响与整改）、规范书覆盖对照。
3. 关键字可粘贴进 Word；页码会漂。
4. 资格与评分分开写；「未提供不得分」的空节打 0。
5. 不要改 Word，除非我明确说改。
```

复核时在提示词末加：`对照 {上一份互审意见路径} 做闭环，标已改/未改/回潮。`

终评时加：`按附件1逐项给分，步长 0.1，客观项用材料算，主观项给档和中位。`
